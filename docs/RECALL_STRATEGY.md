# 召回机制与策略评估

本文回答一个集成层面的问题：**什么时候该召回、召回要付什么代价、接口边界在哪。**
所有数据来自 7.0.0 部署上的实测，标注方式：`[实测]` / `[代码]` / `[推理]`。

> ## ⚠️ 7.0.2 状态更新（读本文前必看）
>
> 本文写于 7.0.0 部署，其中**若干"测评结论"已被 7.0.2 修掉**。历史数据保留备查，
> 但**不要**再拿它们当作当前行为。逐项对照：
>
> | 本文的结论 | 7.0.2 状态 |
> |---|---|
> | §1.3「Path3 为什么恒空」 | ✅ **已修**。抽取器主语去定语归一 + 查询侧代词归一（`我/我的`→`用户`）+ 邻接图多跳。实测 `graph_query('用户')` 由**空** → 10 个邻居节点；`用户的显卡是 RTX 4090` → `用户 --is_a--> RTX 4090 (qualifier=显卡)` |
> | §3 代价②「召回没有相关性下限」 | ✅ **已修**。引入相关性下限（阈值标定自实测：相关簇 cosine min 0.5222 / 无关簇 max 0.4064 → `REL_MIN_SEMANTIC=0.45`）。无关查询现在返回**接近空**的结果，而不是填满 k 条 |

## 1. 召回是怎么工作的

### 1.1 拓扑

```
客户端（MCP / HTTP / CLI / Python SDK）
   │
   ▼
MemoryBrain ──┬──► SQLite  (WAL + FTS5)    记忆正文 / 全文索引
              │      └─ ledger.db          哈希链审计账本（全局共享）
              ├──► 向量后端（可选）          每命名空间一个集合
              │      ▲
              │      │ 1024 维（BGE-M3 示例）
              └──► 嵌入服务（可选）           OpenAI 兼容 /v1/embeddings
```

`[代码]` MCP 服务端路径：`mnemosyne/webui/mcp_server.py`

### 1.2 读取路径 —— 多路并行打分

`[代码]` `retrieval.py`：

| 路径 | 作用 | 实测状态 |
|---|---|---|
| Path1 BM25/FTS5 | 关键词命中 | 正常 |
| Path2a 语义候选召回 | 用向量后端突破 FTS 的 top-K 候选池（`candidate_n=500`） | 正常 |
| Path3 知识图谱 | 实体 2 跳扩展 | **恒空**（见下） |
| Path4 时序 | 时间衰减加权 | 正常 |

最终打分（`retrieval.py`）：

```
total = ( n_bm25×0.12 + n_vec×0.55 + n_graph×0.10 + n_time×0.20 + conf×0.10 )
        × (0.6 + 0.4×importance)
        + access_boost + ngram_boost(≤0.15) + syn_equiv(0.5 if 归一化同形)
```

`[代码]` 语义后端下 **`vec_weight = 0.55`，是权重最高的一路**；
但 `vec_scores[i]` **只在 `record["embedding"]` 非空时才计算**。

### 1.3 Path3 曾经恒空（7.0.2 已修）

`[代码]` `retain` 的 `fast=True` 分支里 `graph_edges` **恒为空数组**，
而 MCP 写入路径固定走 `fast=True`。

`[实测]` 结果是 `graph.jsonl` = **0 字节**。

> **后果：`graph_query` 永远返回 `edges: []`，是一个死工具。**
> 若你的集成流程里包含"结果不足时用 `graph_query` 补足召回"，
> 这条分支**不会带任何增量信息**，纯属白跑。
>
> 补图边属于改动核心记忆逻辑，7.0.1 **未包含**此项。

### 1.4 隔离模型

| 维度 | 是否隔离 | 机制 |
|---|---|---|
| 记忆正文 | ✅ | 命名空间 → 独立 `data/namespaces/<ns>/memory.db` |
| 向量 | ✅ | 命名空间 → 独立集合 `mnemosyne_<ns>` |
| FTS 索引 | ✅ | 随命名空间库走 |
| **审计账本** | ❌ | `ledger.db` 是 brain-dir 根下一个**全局共享**的哈希链 |
| **图谱** | ❌ | `graph.jsonl` 全局 |
| **统计** | ❌ | `stats.json` 全局 |

多 Agent 部署时注意：**正文与向量是隔离的，审计/图谱/统计不是。**

### 1.5 实测性能

| 操作 | 冷（进程内首次） | 热（中位数） |
|---|---|---|
| `recall` | 98.5 ms | **2.4 ms** |
| `recall` + `graph_query` + `temporal_query` 三连 | — | **2.9 ms** |
| 单条 `retain`（`fast=True`，含 encode） | ~6.1 s（首次触达建集合） | ~65 ms |

单次 `recall` 返回 **933 字符**；三工具组合返回 **1202 字符**。

> 冷的那个 ~6 秒是新建集合的成本（见 [KNOWN_DEFECTS.md](KNOWN_DEFECTS.md) 的 F3），
> **不是**稳态延迟。测延迟前先预热一次。

## 2. 接口边界：MCP 是 CLI 的薄子集

`[实测]` 对照两者的参数面：

| 能力 | CLI | MCP |
|---|---|---|
| 写入带 `tags` | ✅ `retain --tags` | ✅ 7.0.1 起 |
| 按时间范围召回 | ✅ `recall --from --to` | ❌ 无 |
| **限制召回 token 预算** | ✅ `recall --budget-tokens` | ❌ 无 |
| 多跳召回 | ✅ `recall --multi-hop` | ❌ 无 |
| 按 layer / type / tag 过滤 | ✅ `--layer --type --tag` | ❌ 无 |
| 删除记忆 | ✅ `forget` | ✅ 7.0.1 起（`forget` 工具） |
| 压缩 / 去重 | ✅ `consolidate` / `dedup` | ❌ 无（只有 `doctor`） |

`[推理]` **按"完整 API 面"设计的集成方案会在 MCP 上落空。**
标签、时间范围、token 预算、多跳这些精细控制在 MCP 面上**没有对应参数** ——
这不是接口写得糙，而是 MCP 层有意做得更薄（13 → 7.0.1 的 14 个工具）。

**需要精细控制时，用 CLI 或 Python SDK，不要试图用 MCP 参数凑。**

### 2.1 MCP 工具面（31 个，8.0.0）

`retain` / `recall` / **`forget`** / `stats` / `retain_batch` / `doctor` /
**`recall_health`** / **`capsule`** / **`expand`** / `graph_query` /
`temporal_query` / `list_projects` / `audit` / `confidence_history` /
`memory/export-v1` / `memory/import-v1` / `memory/claim` /
`consolidate` / `reflect` / `dedup`

（粗体为 7.0.1/7.0.2 新增；7.0.1 为 14 个，7.0.2 增至 20 个。）

> 常见混淆：**没有** `verify_integrity` 工具 —— 完整性校验是 CLI 子命令
> （`mnemosyne --dir <brain> verify-integrity`），MCP 对应工具是 `doctor`。
> `memory/claim` 是**导入合并**工具（入参要 `filepath`），**不是**删除工具。

## 3. "每轮都召回"划算吗？

技术上完全可行：三工具组合实测 **2.9 ms**，时间不是瓶颈。
真正的代价在别处。

### 代价 ①：上下文只增不减（主要成本）

`[实测]` 三工具组合每次返回 1202 字符。**工具结果不会自动清理**，会一直留在上下文里。

| 会话轮数 | 累计注入字符 | 折算 token（估算） |
|---|---|---|
| 10 轮 | ~12,000 | ~8,000 ~ 12,000 |
| 30 轮 | ~36,000 | ~24,000 ~ 36,000 |
| 50 轮 | ~60,000 | ~40,000 ~ 60,000 |

> token 数按中文 0.6~1 token/字**估算**，不是实测。字符数是实测。

### 代价 ②：召回没有相关性下限

`[实测]` 在正确装载向量插件的环境下：

| 查询 | 期望 | 实际排名 | 首条分数 |
|---|---|---|---|
| 我用什么语言跟你沟通 | 命中"简体中文偏好" | **第 1 名** ✅ | 0.8332 |
| 如何烤舒芙蕾蛋糕 | 应该都不相关 | 不命中，但**仍返回 5 条** | 0.8232 |
| 我的显卡是什么型号 | 应该都不相关 | 不命中，但**仍返回 5 条** | 0.8232 |

**排序是对的，但绝对分没有意义**（见 [KNOWN_DEFECTS.md](KNOWN_DEFECTS.md) 的 F6）。
一个完全不相干的查询也拿到 0.82 的高分，所以"置信度 > 0.6"这类阈值**在数值上完全失效**。

`[推理]` 后果：调用方每轮都会拿到 5 条"看起来很像真的相关"的记忆，
而且**没有任何信号告诉它"这条其实不相干"**。在 5 条记忆的小库里 top-5 = 全部，
等于每轮把整库灌一遍。

### 代价 ③：两个"补足召回"的工具在当前实现下恒为空

- `graph_query` → `graph.jsonl` 是 0 字节 → `edges` 恒为 `[]`
- `temporal_query` → 入参是 `entity` 而**不是时间范围**，传"昨天"返回
  `nodes:["昨天"], edges:[]` —— 无意义；真正的按时间过滤在 CLI 的 `--from/--to`

`[推理]` "结果少于 N 条就补调 `graph_query` / `temporal_query`"这条流程，
**触发时拿不到任何增量信息，纯粹是两次白跑**，而且会让模型误以为"已经补足"。

## 4. 该怎么做

### 4.1 原则：分层，而不是"每轮全量召回"

"最了解用户的 AI" ≠ "每轮把库倒一遍"。真正的机制应该是：

1. **写得好** —— 身份/偏好/长期目标进库（而不是靠规则每轮喂）
2. **召得准** —— 只在真正需要历史时召回，并且**有相关性判断**
3. **分层** —— 稳定的画像用"注入"（便宜、恒定），易变的用"召回"（按需）

用"召回"承担"注入"的职责，就必然要每轮召回；一旦每轮召回，成本就爆炸。
**把稳定信息从"召回"挪到"注入"，问题就消失了。**

### 4.2 具体建议

| 优先级 | 建议 | 理由 |
|---|---|---|
| **P0** | 召回结果**按排序取前 3**，由模型判断相关性 | 绝对分无标度意义，相对排序才可靠（F6） |
| **P0** | 不要写"置信度/分数 > X 才算相关"的规则 | 无关查询的分数同样在 0.6 以上（F6） |
| **P0** | "遗忘"一律走 `forget`（7.0.1 起可用） | 7.0.0 没有任何删除工具，`memory/claim` 是导入工具 |
| **P1** | 把"每轮召回"降为**首条 + 触发式召回** | 省下 §3 代价 ① |
| **P1** | 稳定画像用 `retain` 预置进库，规则只留"何时查、何时记" | 数据进库、规则进文件 |
| **P1** | 从强制流程里删掉 `graph_query` / `temporal_query` | 当前实现下二者恒为空/参数不匹配 |
| **P2** | 定期 `consolidate` + `dedup` | 控制库膨胀，提升召回质量 |
| **P2** | 修 `fast` 分支的 `graph_edges`，让图谱真正可用 | `graph_query` 从死工具变活工具（改核心记忆逻辑，需单独评估） |
| **P2** | 补齐脚本增加 `--backfill-sqlite` | 见 F5 |

### 4.3 触发词（供参考）

把"每轮召回"降级后，可用触发词兜住漏召回：
`还记得` / `之前` / `上次` / `我说过` / `我的偏好` / `我的情况`。
